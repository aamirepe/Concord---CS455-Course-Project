01 What Concord is

A CRDT-based collaborative Python IDE: browser clients co-edit files live over Yjs/pycrdt, run code in single-use sandboxed Docker containers, and step through a shared debugger with a single-driver model.

Stack

React 18 + TypeScript + Vite + Monaco + Yjs on the client; FastAPI + SQLAlchemy async + Alembic + Postgres on the backend; Redis for the execution queue and pub/sub; a standalone worker pool driving sibling Docker containers for sandboxed execution.

Who it's for

Students pairing on labs, instructors/TAs reviewing live without taking the editor, and course staff responsible for deployment, monitoring, and load behavior — per docs/requirements.md.

02 Current test coverage

Backend has a real but narrow automated suite. Worker tests exist but never run in CI. Frontend has no test infrastructure at all.

LayerTestsRuns in CI?Covers
backend/tests/ ~18 tests across 6 files yes Auth, breakpoint CRUD + permission, CRDT convergence (10×100 simulated edits), debug session creation, execution FSM transitions, viewer/member permission checks
worker/tests/test_sandbox_security.py 5 tests no Network isolation, timeout kill, read-only fs, fork-bomb/pids-limit, image existence — all gated on DOCKER_TESTS=1, which CI never sets
frontend/ 0 n/a No vitest/jest/cypress/playwright dependency, config, or test file anywhere. CI's frontend job only lints, type-checks, and builds.

Fixture surface in backend/tests/conftest.py is minimal: an in-memory SQLite override, a per-test schema reset, an httpx ASGI client, and a two_users fixture. There are no fixtures for projects, files, executions, mocked Redis, mocked LLM providers, or a WebSocket test client — which is why whole feature areas below have no tests at all rather than partial ones.

04 Concrete coverage gaps

Ordered roughly by risk × how central the code is to the product's core claims (real-time correctness, sandbox safety, permission enforcement).

Realtime WebSocket gateway

The documented wire protocol (hello / sync_step1 / awareness / exec_event_ack, binary vs. JSON framing) and the room-lock serialization behavior have no integration test that opens an actual WebSocket. test_concurrent_edits.py exercises CRDT math directly against a simulated fanout, not the real gateway.

backend/app/realtime/gateway.pybackend/app/realtime/manager.py

LLM assistant feature

Zero tests for API-key encryption/decryption, Redis-based rate limiting with fallback, provider dispatch, or either adapter — despite the assistant router being the largest in the app.

backend/app/llm/manager.pybackend/app/llm/adapters.pybackend/app/api/assistant.py

Worker execution loop

The most complex concurrency in the repo — BRPOP consumption, workspace mounting from DB, concurrent cancel-listening via asyncio.wait, state-transition publishing — has no unit tests at all. Only the resulting container's security properties are tested, and only under DOCKER_TESTS=1.

worker/app/worker.py

Project/file/folder CRUD surface

Projects, files, folders, invitations, snapshots, and metrics endpoints have no dedicated test files — they're only touched incidentally as setup inside other tests, meaning success paths are implied but failure paths (permissions, validation, not-found) are not.

api/projects.pyapi/files.pyapi/folders.pyapi/invitations.pyapi/snapshots.pyapi/metrics.py

Background loops

Checkpoint persistence and orphaned-room sweeping run continuously in production but are never exercised in isolation.

realtime/checkpoint.pyrealtime/orphan_sweep.pyrealtime/execution_queue.py

Debug protocol layer

test_debug.py covers API-level session creation and linking only. DapClient and DebugManager have no isolated unit tests for state handling or DAP protocol correctness.

backend/app/debug/dap.pybackend/app/debug/manager.py

Multi-language runtime paths

Only the Python execution path is exercised. C++ and Node.js build/entrypoint configs in the runtime registry are untested, and there are no negative-path tests for Docker API errors or malformed CRDT updates anywhere in the suite.

backend/app/runtime/registry.py

Frontend — everything

No test runner is installed. Nothing verifies the Editor/Yjs binding, the WebSocket sync client, the file tree, or page-level flows (login, dashboard, session). This is the single largest blind spot in the repo relative to how much user-facing logic lives there.

05 Testing implementation plan

Sequenced so each phase either closes a rubric-visible V&V gap or unblocks the next phase's fixtures. Nothing here has been implemented — this is the order to implement in.

PHASE 1

Wire up what already exists

Before writing new tests, make the existing ones count. Add a worker job to .github/workflows/ci.yml that runs with a real Docker daemon and DOCKER_TESTS=1, so test_sandbox_security.py actually executes on every PR instead of silently skipping. Add a coverage floor (--cov-fail-under) to the backend CI step so coverage can't silently regress while later phases add tests.

PHASE 2

Expand backend fixtures

Extend conftest.py with fixtures for a project + file + folder graph, a fake/queued execution, a mocked Redis client, and a mocked LLM provider. This is the prerequisite for nearly every gap in Section 04 — without it, each new test file re-implements its own setup.

PHASE 3

Close the highest-risk backend gaps

In order: a real WebSocket integration test against gateway.py (covers FR9's debug broadcast requirement as a side effect), project/file/folder/invitation/snapshot CRUD tests including permission-denied paths, and worker unit tests for the execution loop with a faked Docker client. These three map directly to unresolved FR/NFR rows in Section 03.

PHASE 4

LLM assistant & debug protocol

Unit-test LLMManager's key encryption and rate-limit fallback with a mocked Redis, and each adapter with a mocked HTTP layer. Unit-test DapClient/DebugManager state handling independent of the API layer.

PHASE 5

Stand up frontend testing from zero

Add Vitest + React Testing Library (matches the existing Vite setup with least friction), starting with lib/api.ts and lib/ws.ts as pure-logic units, then component tests for FileTree and ErrorBoundary. Defer full Editor.tsx/Yjs binding tests and any E2E tool (Playwright) until this foundation is in place — they're highest-value but also highest-setup-cost.

PHASE 6

Turn manual V&V rows into recorded runs

Run scripts/load_test.py and record actual numbers against FR4/NFR1–3 in the V&V report. Run scripts/chaos.py against FR12 and document the outcome. Neither needs to become a CI gate immediately — recording a real result is the gap, not automation.

06 Beyond testing: open threads

Findings from the docs pass that affect scoping but aren't testing work themselves.

  • Debug mode isn't fully wired end-to-end — docs/HOW_TO_RUN.md notes that debug=True execution isn't yet connected through the Run button; only breakpoint UI/persistence is verified. This should probably land before or alongside the Phase 3 WebSocket/debug tests, or the new tests will be testing a path users can't actually reach yet.
  • Two design patterns are explicitly deferred per docs/design-patterns.md: a Strategy seam at realtime/crdt.py for pluggable CRDT algorithms, and a Factory seam at app/services/sandbox.py for multi-language execution (referred to there as "Feature 17"). Worth confirming whether either is in scope for remaining coursework before Phase 4/5 testing work locks in the current interfaces.
  • docs/build-spec.md is referenced but does not exist — README.md points to a Phase 0–10 build-order document that isn't in the repo. Worth checking whether it was lost, renamed, or never committed, since it may be the canonical source for "what's left."
  • Stray file in the frontend — frontend/src/pages/SessionPage.tsx` (literal backtick in the filename, 9.4KB) sits alongside the real 21.6KB SessionPage.tsx. Not a testing concern, but worth a one-line cleanup so it doesn't get accidentally imported or confused for a WIP file.
  • NFR5 (TLS) is graded, not just functional — explicitly called out as required for the grading demo. Confirm the deploy checklist in docs/runbook.md covers this before the demo date rather than at test time.

07 Recommended sequencing

If only one thing happens next, it should be Phase 1 — it's near-zero effort (CI config, not new tests) and immediately turns five already-written tests from decorative to real. Everything else compounds on Phase 2's fixtures, so resist starting Phase 3+ work in parallel without it.

Suggested order: Phase 1 → Phase 2 → Phase 3 → (Phase 4 and Phase 5 can run in parallel, different surface areas) → Phase 6 last, once there's enough automated coverage that a load/chaos run is measuring the real system rather than a system that still has open correctness gaps.
